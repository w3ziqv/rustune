# Rustune Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans task by task; the user requests autonomous implementation. One independent whole-branch review before publication.

**Goal:** Build a Linux Rust TUI and private playback service using official MusicKit JS.

**Architecture:** One current-thread Tokio service owns playback, queue and state. A lazy Chromium process runs a minimal local MusicKit document controlled exclusively over inherited CDP pipes. A separate TUI connects through a permission-restricted Unix socket, allowing daemon playback and SSH control.

**Tech Stack:** Rust 2024, Ratatui 0.30.2, Crossterm 0.29, Tokio, Serde/TOML, zbus, command-fds.

**Spec:** User's Rustune build brief (2026-11-08); requirements summarized in docs/architecture.md and README.md.

## Global Constraints

- Linux only; no graphical frontend for normal controls.
- No telemetry, hardcoded credentials, password storage, DRM bypass or previews masquerading as songs.
- Real playback is the highest functional priority. Release only after authenticated playback verification.
- Report browser memory separately; unavailable quality/effects remain disabled.

## Review Focus

- Malformed or oversized IPC/config/state data: bounded reads, validation and actionable errors.
- Queue mutations around the current song: preserve identity and never skip unexpectedly.
- Browser death/network/auth expiry: report failures, keep TUI usable and support reconnect.
- Small terminals and Unicode: safe layout and visible controls without panics.
- Another local user or webpage: no tokens on HTTP or debugging ports; private files and socket.
